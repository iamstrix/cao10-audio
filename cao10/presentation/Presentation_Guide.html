1. The 30-second summary

Your one-sentence pitch: "We built a retro game sound-effect generator where every audio sample is computed by hand-written x86-64 Assembly; Python only provides the buttons, the waveform picture and playback."

The program has three layers. Memorise this picture, because most questions are really about which layer does what.

Layer File Language Job
GUI gui/app.py, gui/presets.py Python + Tkinter Sliders, presets, Randomize, draws the waveform, plays and saves the sound
Binding gui/sfx_binding.py Python ctypes Copies the slider values into a 44-byte struct and calls the DLL
Engine engine/sfx.asm (313 lines) NASM x86-64 Assembly Computes the audio samples and builds the WAV file bytes
Proof ref/sfx_ref.c, tests/, bench/ C A C copy of the same algorithm used to check and time the Assembly

What one click does: you move a slider → Python fills the parameter struct → calls sfx_sample_count (how long will it be?) → allocates a buffer → calls sfx_generate (fill it with samples) → calls sfx_write_wav (wrap them in a WAV header) → draws and plays the result.

The audio format: mono, 16-bit signed integers, 44,100 samples per second, at most 5 seconds (220,500 samples, 441,044 bytes as a WAV).

Headline results you can quote:

  • The Assembly output matches the C reference bit for bit: 10,000 random sounds + 20 fixed cases, maximum sample difference 0, 1,279,144 checks passed.
  • Generating a 1-second sound takes 0.33 to 1.68 ms in Assembly (median), well under the 5 ms target.
  • Optimised C (-O2) is faster (0.26 to 0.40 ms). Assembly beats unoptimised C (-O0) on every waveform. Say this openly; it is a strength to be honest about it.
  • The DLL is 5,632 bytes, imports nothing, has no writable memory and uses no heap.

2. Assembly crash course (only what this program uses)

Assembly is a list of tiny steps the CPU runs one after another. Each line does one thing: move a value, add, compare, or jump. You only need about 25 instructions to read sfx.asm.

Registers: the CPU's variables

Registers are a handful of very fast storage slots inside the CPU. This program uses two kinds.

Kind Names used Holds Think of it as
General purpose (64-bit) RAX RCX RDX R8 R9 R10 R11 RSP Integers, pointers (addresses) int and pointer variables
Same, lower 32 bits EAX EDX R8D R9D R10D 32-bit integers uint32_t
SSE (128-bit, we use the low 32 bits) XMM0 to XMM5 One float each float variables
Stack pointer RSP Address of the top of the stack Where local variables live

EAX is just the lower half of RAX. Writing EAX clears the upper half, which is why xor eax,eax sets the whole of RAX to zero.

Reading one line

NASM syntax is instruction destination, source. The result goes into the left operand.

movss xmm0,[rcx+SfxParams.attack]   ; xmm0 = params->attack
mulss xmm0,[rate]                   ; xmm0 = xmm0 * 44100.0
cvttss2si eax,xmm0                  ; eax  = (int) xmm0   (truncate)
  • Square brackets mean memory: [rcx+24] = "the 4 bytes at address RCX + 24".
  • ; starts a comment.
  • SfxParams.attack is a named offset (24) from the struc block, so we never write magic numbers.

The instructions you will meet

Instruction Meaning C equivalent
mov a,b Copy b into a a = b;
lea r,[addr] Compute an address (or do quick maths) without reading memory r = &x; or r = 2*n + 44;
add / sub / inc Integer add, subtract, add 1 a += b; a++;
xor a,a Fast way to set a register to 0 a = 0;
shl / shr Shift bits left / right x << 13, x >> 17
and Bitwise AND i & 255
test a,a Is a zero? (sets flags only) if (a == 0)
cmp a,b Compare integers (sets flags only) if (a < b)
jz / je / jb / ja / jmp Jump if zero / equal / below / above / always if (...) goto
call / ret Call a function / return from it f(); return;
movss Move one float float x = y;
addss subss mulss divss Float add, subtract, multiply, divide + - * /
minss Smaller of two floats fminf(a,b)
comiss Compare two floats (sets flags) if (x < y)
cvttss2si Float → int, truncate (int)x
cvtss2si Float → int, round to nearest lrintf(x)
cvtsi2ss Int → float (float)n
andps Bitwise AND on floats (used to clear the sign bit) fabsf(x)
xorps x,x Set a float register to 0.0 x = 0.0f;
packssdw Squash 32-bit ints into 16-bit with saturation clamp to -32768..32767

Flags and jumps: how if and loops work

There is no if or for in Assembly. Instead, cmp/test/comiss set hidden flags, and the next jump instruction reads them.

 inc r8d          ; n++
 cmp r8d,[rsp+TOTAL]
 jb .loop         ; if (n < total) go back to .loop

That is a for loop. Labels starting with a dot (.loop, .bad) are local to the function above them.

Functions and the Windows x64 calling convention

Windows has a fixed rule for how functions pass data, called the Microsoft x64 ABI. Python and C follow it, so our Assembly must too.

Rule In this program
1st–4th arguments arrive in RCX, RDX, R8, R9 sfx_generate(params, out, capacity) → RCX = params, RDX = out, R8D = capacity
Return value goes in EAX / RAX Sample count or byte count; 0 means error
Volatile registers may be destroyed freely RAX, RCX, RDX, R8–R11, XMM0–XMM5
Non-volatile registers must be restored before returning RBX, RBP, RSI, RDI, R12–R15, XMM6–XMM15
Before a call, reserve 32 bytes of "shadow space" and keep RSP 16-byte aligned sub rsp,152 in sfx_generate

Key design choice: the engine only ever uses volatile registers, so it never has to save or restore anything. A test (tests/abi_probe.asm) proves the non-volatile registers come back untouched.

Sections: where things live in the DLL

Section Contains Writable?
.text The code No
.rdata Constants: 1.0, 44100.0, range tables, sine table, WAV header template No
.pdata / .xdata Unwind info so Windows can walk the stack through sfx_generate if something crashes No

Nothing is writable, so there are no global variables. All working state lives in registers or on the stack.

3. Walkthrough of the key parts

engine/sfx.asm has four routines. Three are exported to Python; one is a private helper.

Routine Lines Inputs Returns One-line job
sfx_sample_count 46–88 RCX = params EAX = planned samples, 0 if invalid Validate the parameters and compute the length
sfx_generate 104–248 RCX = params, RDX = output buffer, R8D = capacity EAX = samples written, 0 on error The synthesizer: produce every sample
noise_next 251–263 R9D = random state XMM0 = random float in [-1, 1) Xorshift random number generator
sfx_write_wav 266–302 RCX = samples, EDX = count, R8 = output, R9D = byte capacity EAX = bytes written, 0 on error Write the 44-byte WAV header + copy samples

3.1 The parameter struct (lines 4–16)

The 44-byte struct is the contract between Python and Assembly. Eleven 4-byte fields, no padding.

Offset Field Type Valid range
0 waveform uint32 0 square, 1 sawtooth, 2 triangle, 3 noise
4 base_freq float 20–4,000 Hz
8 slide float -4 to +4 octaves per second
12 min_freq float 20–1,000 Hz, and ≤ base_freq
16 vib_depth float 0–0.5
20 vib_rate float 0–30 Hz
24 attack float 0–2 s
28 sustain float 0–2 s
32 decay float 0–3 s
36 volume float 0–1
40 seed uint32 1 to 4,294,967,295 (never 0)

The same layout is written three times: NASM struc, C typedef struct in ref/sfx.h, and Python ctypes.Structure in gui/sfx_binding.py. If they disagree, the engine reads garbage.

3.2 sfx_sample_count: validation with a loop over a table (lines 46–88)

Instead of nine separate if checks, the nine float fields (offsets 4 to 36) are checked in one loop against two constant tables, low and high (lines 30–31).

 xor r8d,r8d                 ; i = 0
.validate:
 movss xmm0,[rcx+r8*4+4]     ; x = field[i]   (address = params + 4 + 4*i)
 comiss xmm0,[r9+r8*4]       ; compare x with low[i]
 jp .bad                     ; NaN?  -> invalid
 jb .bad                     ; x < low[i]  -> invalid
 comiss xmm0,[r10+r8*4]      ; compare x with high[i]
 ja .bad                     ; x > high[i] -> invalid
 inc r8d
 cmp r8d,9
 jb .validate                ; loop 9 times
  • Why jp? comiss sets the parity flag when either value is NaN ("not a number"). Without jp, a NaN would slip through, because NaN is neither below nor above anything.
  • After the loop it checks min_freq ≤ base_freq, then converts seconds to samples: A = (int)(attack × 44100) and the same for sustain and decay, using cvttss2si (truncate).
  • Total must be 1 to 220,500 (5 seconds). Any failure jumps to .bad, which returns 0.

3.3 sfx_generate setup: the stack frame (lines 104–152)

sub rsp,152 reserves 152 bytes on the stack. Only volatile registers are allowed, and there are not enough of them, so values that stay constant during the loop are parked in stack slots.

Stack offset Name Holds
0–31 (shadow space) Required by the ABI before any call
32 P params pointer
40 OUT output buffer pointer
48 CAP capacity
52 TOTAL planned sample count
56 A attack end, in samples
60 AS attack + sustain end, in samples
64 D decay length, in samples
68 STEP vibrato phase step per sample = vib_rate / 44100
72 MULT pitch-slide multiplier per sample
76 NOISE current noise value

Why 152 and not 80? On entry RSP is 8 bytes off a 16-byte boundary (the call pushed the return address). 152 = 9 × 16 + 8, so after sub rsp,152 RSP is 16-byte aligned again, as the ABI requires before our own calls. The extra space is spare; total stack use stays under the 256-byte budget.

It first calls sfx_sample_count to validate (reusing the same code, so both functions agree on length), then rejects a NULL or too-small output buffer.

The pitch-slide trick (lines 137–145). A slide of s octaves per second means multiplying the frequency by 2^(s/44100) every sample. SSE has no "power" instruction, so it uses a Taylor series:

2^{x} = e^{x \ln 2} \approx 1 + y + \frac{y^{2}}{2}, \qquad y = x \ln 2, \quad x = \frac{\text{slide}}{44100}

Because |x| ≤ 4/44100 ≈ 0.00009, the next term is about 4 × 10^-14, far smaller than float precision (1.2 × 10^-7). So three multiplies and two adds are exact enough. This is computed once, before the loop.

3.4 The per-sample loop (lines 153–240)

This is the heart of the program. It runs once per sample (44,100 times for a 1-second sound). Register map, from the comment on lines 91–93:

Register Meaning
R8D n, the sample index
XMM3 phase, position inside one wave cycle, 0.0 to 1.0
XMM4 current frequency in Hz
XMM5 vibrato phase, 0.0 to 1.0
XMM0 the sample value being built
XMM1 gain (envelope)
R9D random-number state

Each iteration does seven steps:

  1. Slide the pitch (154–159): freq = freq × MULT, then minss caps it at 20,000 Hz so the phase step can never exceed 1. If freq drops below min_freq (and this is not the first sample), stop early and return n.
  2. Vibrato (160–172): look up a sine value: index = (int)(vib_phase × 256) AND 255 into a 256-entry table. vib = 1 + depth × sine. Advance and wrap vib_phase.
  3. Advance the phase (173–181): phase += freq × vib / 44100. When it passes 1.0, subtract 1 (one full cycle done) and draw a new noise value.
  4. Pick the waveform (182–210): jump to the right shape based on waveform.
    • Square: phase < 0.5 ? +1 : -1
    • Sawtooth: 2 × phase - 1 (a ramp)
    • Triangle: 1 - 4 × |phase - 0.5|; the absolute value is done with andps and a mask that clears the sign bit
    • Noise: the stored random value
  5. Envelope (211–228): attack ramps gain 0→1 (n / A), sustain holds 1, decay ramps 1→0 (1 - (n - AS) / D).
  6. Quantize (229–237): sample × gain × volume × 32767, round to an integer with cvtss2si, then packssdw clamps it to the 16-bit range (-32768..32767) so it can never wrap around.
  7. Store and loop (237–240): write 2 bytes at out + n × 2, n++, repeat while n < TOTAL.

Why a phase accumulator? A wave shape only needs to know "how far through the current cycle am I" (0 to 1). Changing frequency only changes how fast the phase moves, so pitch slides and vibrato come out smooth with no clicks.

No division by zero: if A = 0, n < A is never true, so n / A never runs. If D = 0, the sound ends at AS, so the decay division never runs.

3.5 noise_next: the random generator (lines 251–263)

A 32-bit xorshift generator: three shift-and-XOR steps scramble the state.

x ^= x << 13
x ^= x >> 17
x ^= x << 5

The result is treated as a signed integer, converted to float, and multiplied by 2^-31, giving a value in [-1, 1). Same seed → same sequence, so sounds are repeatable. Seed 0 is rejected because xorshift of 0 is 0 forever (silence).

Noise only changes once per wave cycle, so the "pitch" of noise controls how rough it sounds (low = rumble for Explosion, high = hiss for Hit).

3.6 sfx_write_wav: building the file (lines 266–302)

  1. Check pointers, count (1 to 220,500) and that the buffer holds 44 + 2 × count bytes (computed in one lea r10d,[rdx*2+44]).
  2. Copy the 44-byte header template from .rdata (lines 34–42) byte by byte.
  3. Patch the two size fields: data size at byte 40 = 2 × count; RIFF size at byte 4 = data size + 36.
  4. Copy the samples after the header and return the total byte count.
Header bytes Value Meaning
0–3 RIFF File type
4–7 36 + data size Size of the rest of the file
8–15 WAVEfmt Format chunk follows
20–23 1, 1 PCM, mono
24–31 44100, 88200 Sample rate, bytes per second
32–35 2, 16 Bytes per sample, bits per sample
36–43 data + size Sample data follows

3.7 Unwind data (lines 304–313)

sfx_generate changes RSP and calls other routines, so Windows needs a small description of its stack frame (.pdata + .xdata) to walk the stack if an exception or debugger passes through. It says: "this function's prologue subtracts 152 from RSP". The other routines are leaf functions that never touch RSP, so they need none.

3.8 The Python side, briefly

  • sfx_binding.py loads build/sfx.dll with ctypes, declares argument and return types, allocates the buffers, and turns a 0 return into a Python exception.
  • app.py waits 50 ms after the last slider move before regenerating ("debounce"), so dragging does not flood the engine.
  • Playback uses winsound.PlaySound on a worker thread, so the window does not freeze while sound plays.
  • presets.py defines the 7 presets and constrain(), which keeps GUI values valid (min_freq ≤ base_freq, total length ≤ 5 s), so the engine never rejects normal use.

4b. Your presentation script, in plain English

This is the script to present from. It has no code in it. You never need to read anything off a slide that looks like code. When a slide shows code, point at it and say the plain-English line below. The same script is in each slide's speaker notes in the deck. Words in [brackets] are things to do, not to say.

It runs about 13 minutes. Don't memorise it word for word. Read it aloud twice tonight, then say it in your own words.

Slide 1 — Title

Say this: "Hi everyone. Our project is a sound-effect generator for retro-style video games. Think of the coin sound in Mario, or a laser in an old arcade game. You pick a sound, adjust it with sliders, and the program builds that sound from scratch. The interesting part is that the piece that actually calculates the sound is written in Assembly. Assembly is the lowest-level programming language there is. It's basically the processor's own instructions, written out by hand. Python only handles the window and the buttons. [Point at the four lines at the bottom] Those are the four basic sound shapes our engine can make."

Slide 2 — What the app does

Say this: "This is what you see when you use it. There are seven presets, like Coin, Laser and Explosion, plus a Randomize button. Each slider changes one ingredient of the sound: how high or low it is, whether the pitch slides up or down, a little wobble, how long it lasts, and how loud it is. Every time you move something, the sound is rebuilt instantly, the picture of the wave updates, and you can play it or save it as a normal audio file. A bit of background on how digital sound works: a sound is just a long list of numbers. Each number says how far the speaker should push out at that moment. We make 44,100 of those numbers for every second of sound, which is CD quality."

Slide 3 — Three layers

Say this: "This is the most important slide, so I'll go slowly. Think of a restaurant. [Point left] The Python window is the waiter. It takes your order from the sliders. [Point middle] This middle piece is the order slip. It writes your choices down in a fixed format the kitchen understands. [Point right] And the Assembly engine is the kitchen. It actually cooks the sound. [Point at the five steps] Every click goes through the same five steps: ask the engine how long the sound will be, set aside space for it, fill that space with the sound, wrap it up as an audio file, then show it and play it. We also wrote the exact same recipe a second time in C, which is a more everyday programming language. The app never uses that copy. It's our answer key. We use it to check that the Assembly gets every single number right, and to compare speed."

Slide 4 — The shared form

Say this: "Python and Assembly don't speak the same language, so they need a shared form to fill in. [Point at the row of boxes] This is that form. It has eleven boxes in a fixed order: things like which wave shape, the starting pitch, how long the fade-out is, and the volume. Every box is exactly the same size, so the whole form is 44 bytes. A byte is just the basic unit of computer memory. The Assembly side doesn't know any of the names. It only knows positions. It's like saying 'look at the seventh box' instead of 'look at the fade-in time'. That's why we wrote this layout three times, once per language, and they have to match perfectly. And if anything on the form is out of range or doesn't make sense, the engine refuses to make the sound and just reports an error. It never crashes."

Slide 5 — Three jobs

Say this: "Our engine does exactly three jobs. [Point at each box in turn] One: tell me how long this sound will be. Two: actually make the sound. Three: turn it into a proper audio file. Windows has strict rules about how programs pass information to each other: where each piece of information goes, and where the answer comes back. We follow those rules exactly. [Point at the bottom] The bottom part is about good manners. The processor has a small number of super-fast storage slots. Windows says some of them are yours to scribble on, and some you have to hand back exactly as you found them. Our engine only ever uses the ones it's allowed to scribble on, so it never has to back anything up. We also wrote a separate test that checks we really do leave the others untouched."

Slide 6 — The main loop

Say this: "This is the heart of the program. The engine runs one loop, and every lap of the loop produces one of those numbers we talked about. So it runs 44,100 times for every second of sound. [Run your hand along the seven steps] On each lap it does seven small jobs. One: nudge the pitch up or down a tiny bit if the sound is meant to slide. If it slides too low, the sound just ends early. Two: add a small wobble to the pitch, called vibrato. Three: move forward through the wave. Four: work out the shape: square, sawtooth, triangle or noise. Five: apply the volume fade, meaning fade in, hold, fade out. Six: convert it into the number format audio files use. Seven: save it and go round again. The important values stay inside the processor the whole time instead of going back and forth to memory, and that's why it's fast."

Slide 7 — Four wave shapes

Say this: "So how do we get four different shapes? We keep track of one number called the phase. The easiest way to picture it is a clock hand. It starts at the top, goes round, and after one full lap it's back at the start. Every wave shape is just a simple rule for turning the clock position into a height. [Point at each drawing] Square: high for the first half of the lap, low for the second half. Sawtooth: a steady ramp up, then a drop. Triangle: up, then back down. Noise: a random height that changes once every lap. The nice thing is that changing the pitch only changes how fast the clock hand moves, so pitch slides and wobbles stay smooth."

Slide 8 — Six problems we had to solve ourselves

Say this: "These are six problems that a normal programming language solves for you behind the scenes. In Assembly, we had to solve them ourselves. [Point at each box as you go] One, bad input. If someone sends a value that isn't even a real number, comparisons behave strangely, so we added an extra check that catches it. Two, no power button. The processor has no built-in way to do 'two to the power of something', which pitch slides need, so we used a short maths shortcut. It's accurate because each step is tiny. Three, the clock hand. We cap the pitch at 20,000 vibrations a second, so the hand can never skip more than one lap at a time. Four, making numbers positive. There's no built-in way to do that for decimals, so we use a trick that switches off the minus sign directly. Five, too loud. If a value goes over the maximum, we clip it at the maximum instead of letting it wrap round to a big negative number, which would make a nasty click. Six, random but repeatable. Our noise uses a tiny random-number recipe, so the same starting number always gives exactly the same sound. That's what lets us test it."

Slide 9 — Where the data lives

Say this: "Where does the engine keep its working data while it runs? Only two places. One is the processor's own storage slots. The other is one small scratch area, 152 bytes, that it borrows while it works and gives back when it's done. Think of a sticky note you throw away afterwards. [Point at the diagram] Windows is fussy about the size and position of that scratch area, and 152 is the number that fits its rules. Because the engine doesn't keep anything permanently, lots of parts of a program can use it at the same time without getting in each other's way. We tested a hundred at once. The whole engine file is tiny, about 5.6 kilobytes, and it doesn't depend on anything else."

Slide 10 — Making the audio file

Say this: "The last job is turning all those numbers into a real audio file, a WAV file, the kind any media player can open. A WAV file starts with a short label that tells the player things like 'this is CD quality, one channel'. [Point at the strip] That label is the same every time except for two numbers, highlighted here, which say how big the file is. So the engine copies a ready-made label, fills in those two numbers, puts the sound right after it, and that's a finished file. Python then plays it or saves it."

Slide 11 — How we know it's right

Say this: "So how do we know it actually works? Remember the answer-key copy written in C. We made 10,000 random sounds plus 20 hand-picked ones, including every preset, and compared every single number from our Assembly with the answer key. That's about 1.28 million checks. Our requirement allowed a tiny difference of one; we got zero differences. We also tried to break it. We fed it bad values, checked it never writes outside the space it was given, checked the audio file label one byte at a time, and checked that a tone meant to be 441 vibrations a second really is."

Slide 12 — Speed

Say this: "Now speed. We timed how long it takes to make one second of sound, did that a thousand times, and took the middle result. [Point at the chart] Our goal was under 5 milliseconds, which is five thousandths of a second. Every shape beats that easily. Here's the interesting part. [Point at the red bars] Our first version was noticeably slower than the C version on two of the shapes, sawtooth and triangle. We dug into why, and it came down to one single line of code. That line copied a number in a way that made the processor wait for the previous sample to completely finish before it could start the next one. It's like a queue where nobody can move until the person in front is done. We swapped that line for a different copying instruction that doesn't cause the wait. [Point at the green bars] Those two shapes got about four and a half times faster, roughly the same speed as C, and all 1.28 million correctness checks still passed."

Slide 13 — What we haven't proven yet

Say this: "We also want to be upfront about what we haven't proven yet. All our timings come from one laptop. We haven't done a proper listening test with other people, so we're not claiming the presets sound perfect to everyone. The noise sound is a little muffled, which was a trade-off we chose to keep things simple. And the speed-up from that one-line change was measured in one session, so we'd want to repeat it on another computer. [Point right] These are our next steps."

5. Likely questions and strong answers

The pattern for every answer: give the direct answer in one sentence, then one reason, then point to evidence (a line number, a test or a result file). If you don't know, say "we didn't measure that; here's how we would" rather than guessing.

The tough one: "Why is your Assembly slower than C?"

Short answer: "On square and noise we're within about 15% of optimised C. On sawtooth and triangle we were about 5× slower, and we traced it to a single instruction."

What's going on. Line 161 is movss xmm0,xmm5. When movss copies register to register, it only replaces the low 32 bits of XMM0 and keeps the other 96 bits. So the CPU has to wait for XMM0's old value, which is the previous sample's final result. For sawtooth and triangle that result depends on the phase, so every sample has to wait for the previous sample to completely finish. The CPU can't overlap loop iterations. Square and noise don't depend on the phase in the same way, which is why they're fast.

The proof (tested 27 Oct, on a scratch copy; your repo is unchanged): changing that one line to movaps xmm0,xmm5, which copies all 128 bits, gave these results. All 1,279,144 checks still pass, with max difference 0.

Waveform Original Asm (ms) One-line fix (ms) C -O2 (ms)
Square 0.35 0.26 0.30
Sawtooth 1.58 0.35 0.29
Triangle 1.67 0.40 0.38
Noise 0.32 0.24 0.25

This is a strong answer because it shows real architecture understanding: false dependencies from partial register writes. The deck now says the fix was tested, which is true. If someone asks whether it is in the submitted code, be straight: it was tested on a copy. To say it is in the final code, commit the change to engine/sfx.asm, run build.bat, then rerun tools/run_checks.py.

Other reasons C -O2 is still competitive: the compiler schedules instructions to keep the CPU's execution units busy, and it can keep more values in registers. We prioritised readability and a bit-exact match with the reference.

Design questions

Why write the engine in Assembly and the GUI in Python? The course is about computer architecture, so the part that does real computation is in Assembly. Writing a GUI in Assembly would be thousands of lines of Windows API calls and teach nothing about the CPU. Python's ctypes can call a DLL directly with no glue code.

Why a DLL and not an .exe? A DLL is a library other programs load. Python loads it with ctypes.CDLL. It also lets the C test harness and the benchmark load the exact same file.

Why NASM? It's free, uses the readable Intel syntax, and outputs Windows x64 object files that MinGW's gcc can link into a DLL.

Why float and not double? The output is 16-bit audio. A float has 24 bits of precision, which is already more than 16, so double would add nothing you can hear. Single-precision SSE instructions (...ss) are also what the C reference uses, so they match bit for bit.

Why does Python call sfx_sample_count first? The engine never allocates memory (no heap). So the caller has to ask "how big will it be?", allocate a buffer, and pass it in. That's the same pattern many Windows APIs use.

Why can sfx_generate return fewer samples than sfx_sample_count? With a downward pitch slide, the sound ends early when the pitch drops below min_freq (line 158–159). Python always uses the returned count for the WAV and the drawing.

Assembly questions

Walk me through the main loop. Use slide 6: slide pitch, vibrato, advance phase, pick waveform, envelope, quantize, store, inc r8d, cmp r8d,[rsp+TOTAL], jb .loop.

What are RCX, RDX, R8 here? The first three arguments. Windows x64 passes arguments 1–4 in RCX, RDX, R8, R9. For sfx_generate: params pointer, output buffer, capacity.

Why sub rsp,152? It reserves stack space for 32 bytes of shadow space (required before any call) and 12 local values. 152 makes RSP a multiple of 16 again, because the call into us pushed 8 bytes. Windows requires 16-byte alignment at every call.

Why do you store things on the stack instead of in registers? We only use volatile registers (so nothing needs saving), and there are only six volatile XMM registers. Values that don't change in the loop, like A, D, MULT, go in stack slots. Those are in the L1 cache, so reading them costs about as much as a register.

What's the difference between volatile and non-volatile registers? Volatile (RAX, RCX, RDX, R8–R11, XMM0–XMM5) can be destroyed by any function. Non-volatile (RBX, RBP, RSI, RDI, R12–R15, XMM6–XMM15) must have the same value when you return. If we clobbered XMM6, Python would crash in a confusing way later.

How do you prove you don't corrupt registers? tests/abi_probe.asm fills every non-volatile register with a known pattern, calls our function, then checks that every one is unchanged. It runs on success paths and error paths.

What is jp doing after comiss? It catches NaN. Comparing anything with NaN is "unordered", which sets the parity flag. Without jp, NaN would pass the range check, because NaN is neither below nor above any number.

What's the difference between cvttss2si and cvtss2si? The extra t means truncate (chop off the decimals). We truncate when converting seconds to sample counts so every implementation agrees exactly. We round to nearest when converting the final sample value, which is more accurate audio.

Why packssdw? It packs 32-bit integers into 16-bit with signed saturation: anything above 32767 becomes 32767 and anything below -32768 becomes -32768. Without it, a value like 32768 would wrap around to -32768, which sounds like a loud click.

How does andps compute an absolute value? A float's top bit is its sign. ANDing with 0x7FFFFFFF clears that bit, so -0.3 becomes 0.3. One instruction, no branch.

Explain the Taylor series. A slide of s octaves per second means multiplying the frequency by 2^(s/44100) each sample. SSE has no power instruction. For a tiny x, 2^x ≈ 1 + y + y²/2 with y = x · ln 2. Since x is at most 0.00009, the first ignored term is about 10^-14, much smaller than float precision.

Why cap frequency at 20,000 Hz? Without a cap, a long upward slide would make the phase step bigger than 1. Then one subss wouldn't wrap the phase back into 0–1 and the waveform would break. 20 kHz is also the top of human hearing.

What's default rel? It makes memory references like [rate] relative to the current instruction (RIP-relative). Windows can load a DLL at any address, and RIP-relative addressing still works wherever it lands.

What are .pdata and .xdata? Unwind information. If an exception or a debugger needs to walk the call stack while inside sfx_generate, Windows reads these to know we subtracted 152 from RSP. Leaf functions that never touch RSP don't need them.

Could you divide by zero in the envelope? No. The attack division n / A only runs when n < A, which is impossible if A = 0. The decay division only runs after A + S, and if D = 0 the sound ends exactly there.

What happens with seed 0? Xorshift of 0 is 0 forever, so noise would be silence. The engine rejects seed 0 (line 52–53) and the GUI never sends it.

Why not use SIMD to do 4 samples at once? Each sample depends on the previous one: frequency is multiplied each step, and phase is accumulated. Running 4 in parallel would need a different formula, which would no longer match the C reference bit for bit.

Correctness and testing

How do you know the output is right? We wrote the same algorithm in C, independently, and compared every sample of 10,000 random sounds plus 20 fixed cases. The maximum difference was 0. We also check physical facts: a 441 Hz square wave has 441 cycles per second, and a pitch slide of +1 octave per second reaches 880 Hz after 1 second (±1%).

Couldn't the C and Assembly share the same bug? Yes, if both follow a wrong spec. That's why we also have the physics checks (cycle counts, slide timing, full-scale ±32767), and the WAV header check against hand-written expected bytes.

How do you know you never write past the buffer? Tests surround the buffer with 64 guard bytes of 0xCD and check they're untouched, with capacity one less, equal and one more than needed.

Is it thread-safe? Yes. No global variables are ever written; all state is in registers or on the caller's stack. The Python test runs 100 concurrent calls.

Honest-limits questions

Do the presets actually sound like coins and explosions? "We haven't run the group listening test yet, so we don't claim that. It's on our next-steps list."

Why does noise sound a bit muffled? The noise value only changes once per wave cycle, and the max base frequency is 4 kHz. That limits how bright it gets. It was a known trade-off in our requirements (G-11).

Were benchmarks fair? One laptop (Ryzen 9 8940HX), 100 warm-ups and 1,000 measured runs, median reported. We didn't control background apps or AC power, and we say so in the README.

Why copy the WAV byte by byte? Simplicity. At most 441 KB, it takes well under a millisecond and runs once per sound, not in the hot loop. rep movsb would be the faster option.
