1. Purpose and how to use this document

The proposal explains why the project exists and sketches what it does. This document turns that sketch into requirements precise enough to build and test against. Where the proposal leaves a choice open or is internally inconsistent, this document either makes a recommendation (marked DECISION) or states a rule (marked RULE) so that the engine author, the GUI author and the tester all work from the same contract.

Requirement IDs FR-01 to FR-14 are kept from proposal section 2.8.1 so the final paper stays traceable. New requirements use these prefixes:

PrefixMeaning

Keywords: shall = mandatory; should = expected unless there is a recorded reason not to; may = optional. Priority uses MoSCoW: Must, Should, Could, Won't (this term).

3. Gaps found in the proposal

These were found while turning the proposal into testable requirements. Each has a resolution that the rest of this document follows.

Status (26 October 2026): G-01 to G-10, G-12 and G-13 are now fixed in the proposal itself (sections 2.1.2, 2.1.3, 2.2, 2.6, 2.7, 2.8 and new requirement FR-15), so the proposal and this document agree. G-11 is a known risk and is deliberately left open until the Week 6 listening test.

#Issue in the proposalWhy it mattersResolution in this document
G-01The pseudocode computes 2 ^ (slide / 44100), but SSE has no exponent instruction, and the proposal avoids x87 (which has F2XM1).The engine cannot implement the pitch slide as written.Use a second-order Taylor expansion. The exponent is at most 4/44100 ≈ 9.1e-5, so the error is far below single-precision resolution. See section 7.2.
G-02Return value 0 means "error", but sfx_generate also returns n when the frequency falls below the minimum, which can be 0 at the first sample.The GUI cannot tell a failure from a silent sound.RULE: validation requires min_freq ≤ base_freq, and the minimum-frequency check is skipped for the first sample, so a valid call always writes at least 1 sample. Return 0 then only ever means error.
G-03Upward pitch slides have no upper bound. At +4 octaves/second for 5 seconds the frequency would reach 440 × 220 Hz.The phase step exceeds 1.0, the single phase -= 1.0 wrap fails, and output becomes garbage.RULE: clamp the running frequency to 20,000 Hz with MINSS after each slide step. Maximum phase step is then 30,000 / 44,100 ≈ 0.68 even with full vibrato.
G-04Section 2.1.2 places buffers in .bss; FR-07 and the memory target forbid engine-owned buffers.Writable globals also break thread safety and determinism.RULE: the engine has .text and .rodata only. No .data or .bss writes. All state lives in registers or on the stack.
G-05Noise seed must be nonzero, but nothing says who enforces it. Xorshift with state 0 outputs 0 forever.Noise waveform would produce silence.RULE: engine rejects seed 0 (returns 0). GUI never sends 0.
G-06sfx_sample_count returns the planned length, but sfx_generate may stop early on the minimum frequency.A WAV built from the planned count would contain stale data at the end.RULE: callers shall use the return value of sfx_generate as the sample count for sfx_write_wav and for drawing. sfx_sample_count is only for sizing buffers.
G-07The conversion from seconds to samples (round or truncate) is not stated.sfx_sample_count and sfx_generate could disagree by one sample, and the C reference could disagree with the Assembly.RULE: samples = CVTTSS2SI(seconds × 44100.0f) (truncate toward zero), computed by one shared internal routine.
G-08Vibrato reads sine_table(...), but table size, type and indexing are not given.The C reference cannot match the Assembly bit-for-bit without them.RULE: 256-entry float table in .rodata, indexed by trunc(vib_phase × 256) AND 255, with vib_phase kept as its own accumulator. See section 7.3.
G-09How a 32-bit xorshift value becomes a float sample is not stated.Same as G-08.RULE: treat state as signed 32-bit, CVTSI2SS, multiply by 2-31. Range is [-1.0, 1.0).
G-10Windows x64 treats XMM6 to XMM15 and RBX, RBP, RDI, RSI, R12 to R15 as callee-saved. The proposal mentions saving registers but not which ones.Clobbering XMM6+ corrupts Python's state and causes crashes that are very hard to trace.See IF-03 and IF-04.
G-11Noise changes value once per waveform cycle, and base frequency is capped at 4,000 Hz.Noise is always somewhat muffled; bright hiss for "Hit" may be hard to get.Accepted for now. Revisit after the Week 6 listening test (risk R-05).

4. System context and constraints

4.1 Layers

LayerTechnologyResponsibilityMust not
GUIPython + Tkinter (D-02)Hold current parameters, validate ranges, call the engine, draw the waveform, play and save audio, run benchmarksCompute any audio samples itself
BindingPython ctypes wrapper moduleMirror the parameter structure, allocate buffers, convert return codes into Python exceptionsHold sound state between calls
Enginex86-64 NASM, built as sfx.dllSynthesize samples and build the WAV image in caller-supplied memoryAllocate memory, call the C runtime or Windows API, keep global state

4.2 Data flow for one regeneration

  1. User changes a control. GUI updates its parameter structure.
  2. GUI calls sfx_sample_count(&p). If it returns 0, the parameters are invalid; show the error and stop.
  3. GUI allocates (or reuses) a sample buffer of at least that many int16 values.
  4. GUI calls sfx_generate(&p, samples, capacity) and keeps the returned count n (G-06).
  5. GUI calls sfx_write_wav(samples, n, wav, 44 + 2n) and keeps the returned byte count.
  6. GUI redraws the waveform from samples[0..n-1]. Play and Save use the WAV bytes.

4.3 Fixed constraints

  • Sample rate 44,100 Hz, mono, signed 16-bit little-endian PCM. Not configurable.
  • Maximum sound length 5.0 seconds = 220,500 samples = 441,044 bytes as WAV.
  • One sound at a time (monophonic). No mixing, no music sequencing.
  • User-mode only. The engine never touches audio hardware; playback goes through the operating system.

7. Algorithm specification

This refines proposal section 2.7.2. The C reference shall implement exactly these steps in this order using float (not double) so its output can be compared to the Assembly sample by sample.

7.1 Setup

A = trunc(attack  * 44100.0f)
S = trunc(sustain * 44100.0f)
D = trunc(decay   * 44100.0f)
total = A + S + D                         // validated: 1 .. 220500, total <= capacity
phase = 0.0f
vib_phase = 0.0f
vib_step = vib_rate / 44100.0f
freq = base_freq
slide_mult = pow2_small(slide / 44100.0f) // section 7.2
state = seed
noise = to_float(xorshift32(&state))      // section 7.4

7.2 Pitch slide without an exponent instruction (G-01)

For small x, 2x = ex ln 2 ≈ 1 + y + y²/2 where y = x · ln 2. Here |x| ≤ 4 / 44100, so the next term (y³/6) is about 4e-14, well below the float epsilon of 1.2e-7. Three SSE instructions (MULSS, MULSS, ADDSS) plus constants are enough.

y = x * 0.69314718f
slide_mult = 1.0f + y + 0.5f * y * y

7.3 Per-sample loop

for n = 0 to total - 1:
    freq = freq * slide_mult
    freq = min(freq, 20000.0f)                    // G-03
    if n > 0 and freq < min_freq: return n      // skipped at n = 0; see note below
    idx = trunc(vib_phase * 256.0f) AND 255
    vib = 1.0f + vib_depth * SINE[idx]
    vib_phase = vib_phase + vib_step
    if vib_phase >= 1.0f: vib_phase = vib_phase - 1.0f

    phase = phase + freq * vib / 44100.0f
    if phase >= 1.0f:
        phase = phase - 1.0f
        noise = to_float(xorshift32(&state))

    square:   s = (phase < 0.5f) ? 1.0f : -1.0f
    sawtooth: s = 2.0f * phase - 1.0f
    triangle: s = 1.0f - 4.0f * abs(phase - 0.5f)    // abs via ANDPS with 0x7FFFFFFF
    noise:    s = noise

    if n < A:          gain = n / A
    else if n < A + S: gain = 1.0f
    else:              gain = 1.0f - (n - A - S) / D

    out[n] = saturate_int16(round(s * gain * volume * 32767.0f))
return total

Note on the first sample: at n = 0 with a negative slide, freq = base_freq × slide_mult is slightly below base_freq. If min_freq == base_freq exactly, the loop would return 0. RULE: the minimum-frequency check is skipped for n = 0, so every valid call writes at least one sample.

Envelope edge cases: when A = 0 the first branch is never taken, so there is no division by zero. The same holds for D = 0. Division should be done in float (CVTSI2SS then DIVSS), or by multiplying with precomputed 1/A and 1/D outside the loop, which is faster. Whichever is chosen, the C reference shall do the same.

Vibrato table: SINE[i] = sinf(2π · i / 256) for i = 0..255, generated once by a script and pasted into both the NASM .rodata section and the C reference as identical hex literals (dd 0x...) so both use bit-identical values.

7.4 Noise generator

xorshift32(state):          // Marsaglia 13/17/5
    x = *state
    x ^= x << 13
    x ^= x >> 17             // logical shift (SHR)
    x ^= x << 5
    *state = x
    return x

to_float(x) = (float)(int32_t)x * 4.656612873e-10f    // 2^-31, range [-1, 1)

The seed is copied into a register; the parameter structure is never written (it is const).

7.5 Quantizer

The maximum product is 1.0 × 1.0 × 1.0 × 32767 = 32767, so saturation should never trigger with valid inputs, but it is kept as a safety net. CVTSS2SI rounds to nearest under the default MXCSR. Saturation can use PACKSSDW as the proposal states, or a compare-and-clamp; either is acceptable if TC-E-09 passes.

15. Benchmark methodology (FR-14)

  1. Implementations compared: Assembly DLL; C reference at -O2; C reference at -O0 (shows what the compiler adds); optional pure-Python version.
  2. Workload: 1-second sound (44,100 samples) for each of the 4 waveforms, vibrato on, slide on.
  3. Timing: QueryPerformanceCounter in the C harness (Python uses time.perf_counter_ns). 100 warm-up runs, then 1,000 measured runs. Report median and 95th percentile.
  4. Machine notes recorded with each result: CPU model, power plugged in, Windows power mode, other apps closed.
  5. Also report: DLL size vs C reference object size; number of instructions in the inner loop (from the listing, nasm -l).
  6. All runs on at least two members' laptops to show the result is not machine-specific.
  7. Expectation to state honestly in the paper: -O2 C may match or beat the Assembly. That outcome is still a valid finding, and the analysis of why (for example, the compiler's register allocation or vectorisation) is part of the deliverable.

20. Glossary

LSB
Least significant bit; here, a difference of 1 in a 16-bit sample value.
Phase
Position within one waveform cycle, from 0.0 to just under 1.0.
Envelope (ASD)
Volume shape over time: attack (rise), sustain (hold), decay (fall).
Volatile / nonvolatile register
Under Windows x64, a function may freely change volatile registers but must restore nonvolatile ones before returning.
Shadow space
32 bytes the caller reserves on the stack for the callee's first four register arguments.
Golden test
A test that compares output against a trusted reference (here, the C implementation).
Debounce
Waiting briefly after the last slider movement before regenerating, to avoid redundant work.
